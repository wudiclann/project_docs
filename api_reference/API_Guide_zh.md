# 如何撰写 API 参考文档 — 指南

本指南说明什么是 API 参考文档（API 文档）、它与 SDD 的关系、如何使用模板，以及每个章节应写什么。

**配合以下文件使用：**
- [API_Template_zh.md](API_Template_zh.md)：可复制并填写的空白模板
- [API_Sample_In-App_Feedback_zh.md](API_Sample_In-App_Feedback_zh.md)：一份完整示例，让你看到"好的 API 文档"是什么样子。示例是虚构的，与 PRD、DRD、TRD、SDD 示例相匹配，因此其中的名称和数字仅作说明，不是默认选项。
- [openapi_Sample_In-App_Feedback.yaml](openapi_Sample_In-App_Feedback.yaml)：示例参考文档所依据的 OpenAPI 文件
- [SDD_Guide_zh.md](../software_design_document/SDD_Guide_zh.md)：API 背后的详细设计

## 第一部分：API 文档基础

### 什么是 API 参考文档？

API 参考文档告诉**调用你服务的人**它做什么、怎么用：如何认证、每个端点接收和返回什么、可能出现哪些错误、有哪些限制，以及各版本之间有什么变化。读者永远看不到你的代码。

它是一份**活文档**。它不像 PRD、DRD 和 TRD 那样批准一次就不再改动，也不像 SDD 那样最终变成一份记录。只要 API 还在被使用，它就必须保持准确。

### API 参考文档 与 SDD

| | SDD（第 5 章，接口详情） | API 参考文档 |
|---|-----------------------------------|---------------|
| 读者 | 构建和维护服务的工程师 | 所有调用它的人：App 和网页开发者、其他团队、合作伙伴、QA |
| 问题 | *为什么这样构建？内部怎么运作？* | *我能调用什么？会得到什么？* |
| 包含 | 每个端点的权限、副作用、内部规则、队列消息、服务内部的错误处理 | 端点、schema、示例、认证、限制、错误码、重试建议、变更日志 |
| 不包含 | 面向公众的教程和快速开始 | 表、队列、重试时间、内部服务 |
| 撰写者 | 工程师，在设计时撰写 | 工程师，主要由代码**生成** |
| 生命周期 | 构建期间变化；最终成为实际构建的记录 | 随每次 API 变更而变化，只要 API 还在使用 |

一个快速判断：如果调用方需要它来**正确使用 API**，放进 API 参考文档。如果工程师需要它来**构建或维护服务**，放进 SDD。

### 唯一事实来源

**OpenAPI 文件**是唯一事实来源。它由代码生成（例如 NestJS 的装饰器、Spring 的注解或 FastAPI 的 schema），或者在契约优先的项目中先写好契约，再在 CI 中与代码核对。

```text
代码或契约  ->  openapi.yaml  ->  发布的 API 参考文档
                    ^
                    |-- SDD 第 5 章链接到这里（不复制）
```

- **SDD 链接**到 OpenAPI 文件和已发布的参考文档，只保留文件说不了的内容。
- **API 参考文档**就是这个文件，加上工具写不出来的页面（概述、快速开始、规则、重试建议、变更日志）。
- 如果模板和 OpenAPI 文件不一致，以文件为准。修正文档。

### 你需要写吗？

| 情况 | 怎么做 |
|-----------|------------|
| 只有你自己的团队调用该服务 | SDD 第 5 章就够了。不需要单独的参考文档。 |
| 其他团队、移动端或网页端调用它 | 编写 API 参考文档。尽早约定契约，让各方并行开发。 |
| 合作伙伴或公众调用它 | 发布参考文档，并附变更日志、弃用政策和入门指南。 |

### API 参考文档不是什么

| API 参考文档不是…… | 原因 |
|----------------------------|------------|
| SDD 的副本 | 调用方不需要你的内部细节。不要链接任何内部内容。 |
| 手工输入的 schema | 它们会过时。请从 OpenAPI 生成。 |
| 整个产品的教程 | 只讲 API。其余部分链接到产品文档。 |
| 对内部实现的承诺 | 只写调用方可以依赖的内容。其他的都可能改变。 |

### 谁会读它，关注什么

| 读者 | 关注点 |
|--------|-------------|
| 刚上手的开发者 | 第 1.3 和第 2 章：一个能跑通的首次调用 |
| 正在开发功能的开发者 | 第 5 和第 4 章：字段、规则、错误 |
| QA | 第 3、4、5 章：限制、错误码、边界情况 |
| 其他团队的工程师 | 第 3 和第 7 章：版本管理以及什么可能改变 |
| 值班或客服人员 | 第 4 和第 8 章：错误是什么意思、联系谁 |

### 写作原则

1. **从一个能跑通的示例开始。**成功调用过一次的人，理解其余内容会快得多。
2. **写调用方可以依赖的内容。**说明有保证的部分，省略只是"目前这样实现"的部分。
3. **要精确。**限制、长度、允许的取值和超时都用数字，而不是"合理"。
4. **给出真实示例。**使用逼真的请求和响应，而不是 `string`。
5. **解释每个错误。**每个错误码：何时发生，调用方应该怎么做。
6. **说明什么可以安全重试。**大多数集成缺陷来自重复提交或被漏掉的重试。
7. **不要泄露内部细节。**不要出现表名、队列名或内部服务名。它们会制造你无法摆脱的依赖。
8. **与代码保持同步。**在修改 API 的同一次变更中更新文档。

## 第二部分：撰写流程

不要从上到下填写模板。更好的顺序：

| 步骤 | 做什么 | 章节 |
|------|---------|----------|
| 1. 约定契约 | 从 TRD 的接口概览中取出端点；与调用方约定形态 | 5 |
| 2. 给代码加注解 | 添加摘要、说明、示例和错误响应，使 OpenAPI 文件完整 | 5 |
| 3. 生成文件 | 构建 `openapi.yaml`；在 CI 中与运行中的代码核对 | — |
| 4. 描述通用约定 | 认证、版本、分页、限制 | 2, 3 |
| 5. 记录错误 | 一张表，写明每种错误该怎么办 | 4 |
| 6. 写快速开始 | 一条完整的端到端路径，附可复制粘贴的调用 | 1 |
| 7. 补充其余内容 | Webhook、变更日志、支持 | 6, 7, 8 |
| 8. 测试示例 | 在预发布环境运行每一个示例 | 全部 |
| 9. 发布并通知 | 放在调用方找得到的地方；从 SDD 链接过来 | — |

### 选择篇幅

| 情况 | 包含 | 可省略 |
|-----------|---------|------|
| **完整**：合作伙伴或公众 | 全部，外加入门指南 | 无 |
| **标准**：内部其他团队（默认） | 第 1–5、7、8 章 | 没有 Webhook 时省略第 6 章 |
| **简短**：为另一个团队提供一两个端点 | 1.3、2、4、5 | 其余部分。一页就够了。 |

## 第三部分：逐章指南

每一章包括：**用途**、**写什么**、**小贴士**和**常见错误**。

---

### 文档头部

**写什么：**API 名称、API 版本和文档版本、基础 URL、状态（预览 / 测试版 / 稳定 / 已弃用）、负责人和联系方式、最后更新日期、OpenAPI 文件的链接、SDD 和 TRD 的链接。

**常见错误：**没有负责人或联系方式。调用方需要知道该问谁。

---

### 1. 概述

**用途：**让读者一分钟内判断这个 API 是否是他们需要的，并在五分钟内完成第一次调用。

**写什么：**
- 1.1：它做什么，用简短列表说明
- 1.2：适用对象
- 1.3：快速开始，附一条完整路径上可复制粘贴的调用

**小贴士：**密钥使用占位符（`$TOKEN`）。展示响应，并说明哪些内容要保留给下一次调用使用。

**常见错误：**快速开始漏掉了某一步（例如怎么拿令牌），导致第一次就失败。

---

### 2. 认证

**用途：**回答"我怎么进去？"以及"我为什么得到 401 或 403？"

**写什么：**凭据从哪里来、如何发送、谁被允许、失败时会怎样，以及调用方请求别人的数据时会怎样。

**小贴士：**如果你用 `404` 来隐藏其他用户的数据，请写明，否则调用方会困惑。永远不要在文档里放真实令牌。

---

### 3. 通用约定

**用途：**适用于所有端点的规则，只写一次。

**写什么：**格式、版本以及什么算破坏性变更、标识符、时间戳、枚举值、重试和幂等、分页、数据窗口，以及一张**速率限制表**（3.1）。

**小贴士：**告诉调用方要**忽略不认识的字段**。这一句话就能让你在不升级版本的情况下新增字段。

**常见错误：**缺少速率限制，或只写"合理"。

---

### 4. 错误

**用途：**让调用方有意识地处理每一种失败。

**写什么：**错误响应体写一次，一张错误码表并写明每种该怎么办（4.1），以及一张重试表（4.2）。

**小贴士：**
- 调用方应根据稳定的 `code` 分支处理，而不是根据消息文字。
- 如果文案由客户端负责，写明 API 返回的是 key，而不是展示用文字。
- 说明哪些错误可以重试，哪些不可以。

**常见错误：**只列出错误码，没说该怎么办。

---

### 5. 端点

**用途：**参考文档本身。

**写什么：**每个端点一个块：方法和路径、用途、谁可以调用、限制、请求字段、响应、副作用、错误。表格从 OpenAPI 生成，再补充工具写不出来的说明。

**小贴士：**
- 先写出人意料的地方：幂等、链接的有效期、"读取即标记为已读"。
- 把每个错误码链接回第 4 章。
- 给出常见情况的示例，以及一个错误的示例。

**常见错误：**只写正常路径。

---

### 6. 事件与 Webhook

**用途：**告诉调用方如何得知有东西发生了变化。

**写什么：**事件、载荷、签名校验、重试行为，以及接收方应如何应答。如果没有，用一句话说明，并说明调用方应如何关注变化（轮询、推送）。

**常见错误：**直接删掉这一章，让读者疑惑到底有没有 webhook。

---

### 7. 变更日志与弃用

**用途：**让调用方能够为变化做计划。

**写什么：**带日期和变更的版本表、弃用政策（通知期、并行运行期），以及什么算破坏性变更。

**小贴士：**在修改 API 的同一次变更中添加记录。清楚标出破坏性变更。

---

### 8. 支持

**写什么：**在哪里提问、在哪里报告本文档的错误、在哪里报告生产环境问题。

## 第四部分：使用 OpenAPI

| 主题 | 建议 |
|-------|--------|
| 生成，不要手写 | 使用框架自带的 OpenAPI 支持。手工编辑的文件会与代码脱节。 |
| 在 CI 中检查 | 在构建中重新生成文件，如果与已提交的副本不同就让构建失败。 |
| 填好描述 | 没有描述和示例的生成文件只是 schema，不是参考文档。在代码中添加摘要、字段说明和示例。 |
| 复用错误响应 | 把常见错误在 `components/responses` 下定义一次，然后引用。 |
| 把内部端点排除在外 | 只有内部系统才会调用的端点（例如供应商的 webhook）写在 SDD 里，不放进公开文件。 |
| 渲染出来 | Swagger UI、Redoc 等工具可以把文件变成可浏览的页面。再补上手写的页面。 |
| 校验它 | 在 CI 中运行 OpenAPI 检查工具（linter）。 |
| 管理版本 | `info.version` 字段是 API 文档版本。每次调用方能看到的变化都要升级它。 |

## 第五部分：质量检查清单

**准确性**
- [ ] 参考文档由 OpenAPI 文件生成，而该文件由代码生成或与代码核对
- [ ] 每个示例都已在真实环境中运行过
- [ ] 限制、长度和允许的取值与代码、SDD、DRD 一致

**易用性**
- [ ] 新调用方仅凭快速开始就能完成一次成功调用
- [ ] 认证已说明，包括失败的情况及原因
- [ ] 每个错误码都写明了调用方该怎么办
- [ ] 说明了哪些调用可以安全重试，以及如何重试

**完整性**
- [ ] 速率限制、分页和数据窗口已说明
- [ ] 版本管理、破坏性变更规则和弃用政策已说明
- [ ] 有负责人、联系方式和变更日志
- [ ] 没有遗留的 `[方括号]` 或引导语

**安全**
- [ ] 没有内部名称（表、队列、内部主机）或真实密钥
- [ ] 仅供内部使用的端点已排除
- [ ] 示例中没有真实的个人数据

## 第六部分：常见错误速览

| 错误 | 修正 |
|---------|-----|
| 手工重打 schema | 从 OpenAPI 生成 |
| 把 API 部分复制进 SDD | 在 SDD 中链接到参考文档 |
| 快速开始跑不通 | 发布前在预发布环境运行一遍 |
| 错误没有对应操作 | 每一行都加上"调用方应该怎么做" |
| 没有重试指引 | 说明什么可以安全重试，以及复用哪个 key |
| 描述内部实现 | 描述调用方可以依赖的内容 |
| 改了 API 没改文档 | 在同一次变更中同时更新两者 |
| 没有变更日志 | 调用方能看到的每次变化都添加一条记录 |
| 只有占位符的示例（`"string"`） | 使用逼真的值 |

---

## 第七部分：让 API 参考文档保持有用

当调用方不用问你一个问题就能完成集成，并且信任自己读到的内容时，API 参考文档就物有所值。

- **随 API 更新。**在与 API 相同的 pull request 中修改参考文档。
- **测试它。**在 CI 中或每次发布前运行示例。
- **关注提问。**调用方的每个问题都说明文档有缺口。修正文档，而不只是回答问题。
- **公布变更。**使用变更日志和发布说明。对于破坏性变更，兑现你承诺的并行运行期。
- **干净地退役。**先把版本标记为已弃用，再移除；并且要等流量停止之后才移除。

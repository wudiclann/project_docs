# 如何撰写 TRD — 指南

本指南说明什么是技术需求文档（TRD）、如何使用模板，以及每个章节应写什么。

**配合以下文件使用：**
- [TRD_Template_zh.md](TRD_Template_zh.md)：可复制并填写的空白模板
- [TRD_Sample_In-App_Feedback_zh.md](TRD_Sample_In-App_Feedback_zh.md)：一份完整示例，让你看到"好的 TRD"是什么样子。示例是虚构的，与 PRD 和 DRD 示例相匹配，因此其中的技术栈、量级和阈值仅作说明，不是默认选项。
- [PRD_Guide_zh.md](../PRD/PRD_Guide_zh.md) 和 [DRD_Guide_zh.md](../DRD/DRD_Guide_zh.md)：TRD 所依托的文档。

## 第一部分：TRD 基础

### 什么是 TRD？

TRD 描述**产品需求将如何被构建**：架构、数据、接口、安全、可靠性、测试和发布。它是产品需求与代码之间的契约。研发据此开发，评审人在工作开始前据此提出质疑，测试、SRE 和安全团队据此规划工作。

通常由技术负责人或负责该功能的工程师撰写，并听取架构、安全和运维的意见。

### 三份文档如何配合

| | PRD | DRD | TRD |
|---|-----|-----|-----|
| 回答 | 做什么、为谁做、为什么、如何衡量？ | 界面上长什么样、怎么表现？ | 我们如何构建和运行？ |
| 作者 | 产品经理 | 交互 / UX 设计师 | 技术负责人 |
| 核心内容 | 问题、目标、用户故事、规则、指标 | 结构、流程、线框图、状态、全局规则 | 架构、数据、API、安全、测试、发布 |
| 主要读者 | 所有人 | 研发、测试、视觉设计 | 研发、测试、SRE、安全、架构师 |

TRD 不应重复另外两份文档。按编号（US-001、DR-003）链接过去，并说明由此产生的技术后果。

### TRD 不是什么

| TRD 不是…… | 原因 |
|-----------------|------------|
| 产品说明 | 功能为什么存在、谁需要它，属于 PRD。 |
| UI 规格 | 布局和界面行为属于 DRD。 |
| 代码堆砌 | 它描述设计和契约，而不是逐行实现。 |
| 空泛愿望的容器 | "可扩展、安全"在没有数字和测试时毫无意义。 |
| 启动会后就完成 | 决策变化时要保持更新，并记录变更。 |

### 谁会读它，关注什么

| 读者 | 关注点 |
|--------|-------------|
| 研发 | 第 2–6 章：架构、数据、行为、接口 |
| 架构师 / 评审人 | 2.4、7、8、12 节：决策、安全、非功能目标、风险 |
| 测试 | 第 4、5、10 章：行为、错误码、测试计划 |
| SRE / 运维 | 第 8、9、11 章：目标、告警、部署、回滚 |
| 安全 / 合规 | 3.4、7 节：数据生命周期、威胁模型、控制措施 |
| 产品 / 设计 | 1.2、8 节：技术方案是否覆盖需求和质量目标？ |

### 写作原则

1. **全程可追溯。**每个技术条目都应来自某个 PRD 或 DRD 需求，或某项明确说明的非功能需求。如果说不清它为什么存在，就质疑它。
2. **用数字。**"p95 < 300 ms"、"月度 99.9%"、"1 小时内重试 5 次"。如果还不知道，就写出问题并指定负责人。
3. **为失败而设计。**对每个依赖，说明它变慢、宕机或出错时会发生什么。
4. **记录决策和替代方案。**不写被否决方案的决策，很难被质疑或重新审视。
5. **精确陈述契约。**输入、输出、错误码、限制和版本，不留猜测空间。
6. **可测试、可运维。**每条需求都要有验证方式；每次上线都要有看板、告警和回滚方案。
7. **如实说明假设。**把估算标为估算，并说明你将如何验证。
8. **规模适度。**跳过不适用的章节（见"选择文档规模"）。

## 第二部分：撰写流程

不要从上到下依次填写模板。更好的顺序：

| 步骤 | 做什么 | 对应章节 |
|------|---------|----------|
| 1. 阅读 PRD 和 DRD | 列出每条有技术后果的需求；记录约束和待决问题 | 1.2、1.4 |
| 2. 估算问题规模 | 估算量级、峰值、增长、数据大小 | 1.4、8 |
| 3. 勾勒架构 | 上下文和容器，然后是组件和技术 | 2 |
| 4. 做出并记录决策 | 对每个真正的选择，列出方案及理由 | 2.4 |
| 5. 建模数据 | 实体、约束、访问模式、生命周期 | 3 |
| 6. 说明行为 | 按功能写输入、输出、规则、状态、错误 | 4 |
| 7. 定义接口 | API、错误目录、版本管理、集成、队列 | 5、6 |
| 8. 加入安全 | 认证、数据保护、威胁、审计 | 7 |
| 9. 设定质量目标 | 性能、可用性、可靠性、SLO | 8、9 |
| 10. 规划测试和发布 | 测试层级、流水线、发布、回滚 | 10、11 |
| 11. 列出风险并规划工作 | 带缓解措施的风险；里程碑 | 12、13 |
| 12. 评审 | 与架构、安全、SRE 和客服 / 运营一起过检查清单 | 15 |

### 选择文档规模

| 场景 | 包含 | 省略 |
|-----------|---------|------|
| **完整版**：新服务、多团队、敏感数据或大规模 | 全部 | 无 |
| **标准版**：典型功能（默认） | 第 1–5、7–13、15–16 章 | 没有队列时省略事件（6）；仅由人类实现时省略 agent 指令（14） |
| **快速版**：现有服务内的小改动 | 1、2.1、3（变更的表）、4、5（变更的端点）、8、11 | 架构决策、事件、除新增风险外的威胁模型、实施计划 |

## 第三部分：逐章指南

每个章节包括：**作用**、**写什么**、**技巧**和**常见错误**。

---

### 文档头部

**作用：**显示这是哪个版本、谁负责，以及它基于哪份 PRD 和 DRD。

**写什么：**版本、作者、技术负责人、评审人、状态、日期，以及 PRD（含版本）、DRD（含版本）、代码仓库和设计文档的链接。

**常见错误：**没有记录 PRD / DRD 的版本，导致没人知道需求是什么时候变的。

---

### 1. 概述与范围

#### 1.1 目的

两三句话：构建什么，以及它服务于哪项产品需求。

#### 1.2 需求追溯

**写什么：**一张表，把每个有技术后果的 PRD / DRD 条目（包括目标和非功能标准）映射到实现它的 TRD 章节。

**技巧：**尽早做，并随进展更新。没有对应 TRD 章节的需求是缺口；没有对应需求的 TRD 章节可能是范围蔓延。

#### 1.3 技术范围

**写什么：**范围内是什么，范围外是什么（附原因），以及环境假设（云、现有平台服务）。

#### 1.4 约束与假设

**写什么：**固定的选择、写明若不成立的影响及验证方式的假设，以及对其他团队的依赖和兜底方案。

**技巧：**把量级估算放在这里，并附上推导过程（"85,000 订阅用户 ÷ 60 天 × 15%"）。这样评审人可以质疑推理，而不是一个光秃秃的数字。

**常见错误：**没有标注的猜测；没有负责人或日期的依赖。

---

### 2. 系统架构

#### 2.1 架构概览

**写什么：**一张图，展示系统、用户、主要可部署部分和外部系统。采用 C4 的思路：先画上下文，再画容器；只有在复杂度需要时，才补充组件级图。

**技巧：**展示数据流方向。用不同方式标记同步和异步链路。图中的每个方框都应出现在 2.2 中。

#### 2.2 组件

**写什么：**对每个组件：单一职责、对外提供和依赖什么、技术、负责人。

**常见错误：**一个组件承担三项职责（"处理请求、同步数据、发送邮件"）——要么拆分，要么说明理由。

#### 2.3 技术栈

**写什么：**按层列出选型、版本，以及理由或约束。

**技巧：**说明哪些选型是被强制的（由公司标准或 PRD 决定），哪些是你自己的选择。

#### 2.4 架构决策

**写什么：**每个重要决策一行：选择、替代方案、理由（权衡、成本、风险）和状态（提议中、已采纳、已取代）。

**技巧：**记录那些难以回退或容易被遗忘的决策：同步 vs. 异步、自建 vs. 采购、状态存放在哪里。如果推理很长，写一份独立的 ADR 并链接过去。

#### 2.5 部署模型

**写什么：**托管、运行时、区域、环境，以及用于发布的任何功能开关。

---

### 3. 数据模型

#### 3.1–3.2 实体与详情

**写什么：**一张 ER 图，然后对每个实体列出每个字段的类型、是否必填、约束和备注（标出个人数据）。

**技巧：**
- Mermaid 实体名称使用下划线（`ORDER_ITEM`）；连字符可能导致渲染失败。
- 枚举要完整写出。说明哪些是唯一的，哪些是外键。

#### 3.3 索引与查询模式

**写什么：**先写真实的访问模式，再写服务于每种模式的索引，并附预期量级。

**常见错误：**"以防万一"而加索引，或者漏掉频率限制或列表页真正需要的那个索引。

#### 3.4 数据生命周期

**写什么：**保留期、删除或匿名化（包括用户删除请求）、备份、恢复点目标和恢复时间目标。

**技巧：**个人数据需要一条覆盖所有副本（对象存储、第三方工具）的删除路径。

#### 3.5 迁移与初始数据

**写什么：**迁移工具、策略（线上系统用 扩展 → 迁移 → 收缩）、每次迁移的回滚、现有数据的回填。

---

### 4. 技术功能需求

**作用：**PRD 功能说明的技术对应部分。它精确说明系统为每个功能做什么。

**每个功能包含：**

| 字段 | 填写内容 |
|-------|-------------|
| 追溯至 | PRD / DRD 编号 |
| 优先级 | 来自 PRD |
| 描述 | 系统做什么，用技术语言描述 |
| 输入 / 输出 | 字段、类型、限制；结果和副作用 |
| 校验规则 | 服务端检查——永远不要信任客户端 |
| 状态流转 | 如果对象有生命周期，画状态图 |
| 错误处理 | 每种失败情形 → 行为、错误码、重试 |
| 副作用 | 通知、第三方调用、审计记录 |
| 幂等性 | 同一请求到达两次时会发生什么 |

**技巧：**考虑重复、重试、部分失败、并发、顺序和过期数据。针对每种失败，用 DRD 中的措辞说明客户端看到什么。

**常见错误：**只写主流程；校验只在 UI 里描述；没有回答"如果这个请求被发送两次怎么办？"。

---

### 5. 接口规格

#### 5.1–5.2 API

**写什么：**先是端点表（方法、用途、认证、是否幂等、频率限制），然后对每个端点写：请求、响应、字段校验，以及错误表（HTTP 状态码、错误码、条件、客户端行为）。

**技巧：**
- 使用统一的错误码格式（`VAL-001`、`AUTH-001`、`RATE-001`、`SYS-001`），让客户端把错误码映射到提示文案。
- 当暴露资源存在与否会泄露信息时，返回 `404` 而不是 `403`。
- 发布一份 OpenAPI 文件，并保持它由代码生成，或者反过来，但不要两边都手写。

#### 5.3 版本管理与兼容性

**写什么：**版本方案、兼容性承诺和弃用政策。

**技巧：**移动应用的旧版本会存在好几个月。写明旧版本必须继续工作多久。

#### 5.4 外部集成

**写什么：**系统、方式、用途、限制、失败行为、负责人。

**技巧：**向负责人确认真实的频率限制和套餐限制。说明依赖宕机时会发生什么，而不只是"重试"。

---

### 6. 事件与消息 *（可选）*

**作用：**描述把各组件串联起来的队列和事件。

**写什么：**拓扑（名称、生产者、消费者、载荷、是否保序）和可靠性规则：投递保证、重试与退避、死信处理、幂等性、schema 演进。

**技巧：**假设至少一次投递，并让消费者具备幂等性。说明谁来查看死信队列、多快查看。

**常见错误：**重试永远不会成功的错误（校验失败）；死信队列没有告警。

---

### 7. 安全架构

#### 7.1–7.2 认证、授权与数据保护

**写什么：**用户和服务如何认证；授权模型（包括对象级检查）；传输和静态加密；密钥处理；个人数据如何存储、访问，以及如何不进入日志。

#### 7.3 威胁模型

**写什么：**针对这个系统真实的数据流：威胁、适用位置、可能性和影响、缓解措施，以及如何验证。

**技巧：**逐条走查每条数据流和信任边界。问：谁可能滥用它？如果有人猜到了 ID 会怎样？如果文件并非它声称的类型会怎样？如果 webhook 被伪造会怎样？力求现实的威胁，而不是教科书清单。

#### 7.4 审计与合规

**写什么：**敏感操作记录什么、保留多久，以及满足法律要求的技术控制。

**常见错误：**列出"OWASP Top 10"却不与本系统挂钩；把安全当作最后一周的工作。

---

### 8. 非功能需求

**作用：**带数字、带验证方式的质量目标。

**写什么：**类别、要求、目标值和验证方式。涵盖性能、吞吐量、可用性、可靠性、可扩展性、容量、兼容性和可维护性。

**技巧：**
- 从 PRD 的非功能标准和 DRD 的第 7 章出发，再补充技术层面的要求。
- 在文档里做容量推算（行数 × 大小 × 增长）。
- 把"依赖宕机时会发生什么"作为可靠性目标写进去。

**常见错误：**"快""高可用""安全"却没有数字；无法度量的目标。

---

### 9. 可观测性与运维

**写什么：**
- **SLO**：度量什么、目标值、告警。
- **日志、指标、追踪**：必须记录什么（以及不得记录什么）、关键指标（包括队列深度和死信队列大小）、trace 传递、看板。
- **告警**：阈值、严重级别、负责人、运行手册。

**技巧：**按使用者来建看板：SRE、客服和产品需要的不同。上线前测试告警。每条告警都应有运行手册。

**常见错误：**没人负责的告警；泄露个人数据的日志。

---

### 10. 测试计划

**写什么：**对每个层级（单元、契约、集成、端到端、性能、安全、韧性、隐私）：范围、目标或标准、负责人。再加一张表，把 PRD 验收标准映射到测试层级。

**技巧：**
- 契约测试保护其他团队和旧版客户端不被破坏性变更影响。
- 韧性测试证明你所设计的失败行为：屏蔽一个依赖、杀掉一个 worker、发送重复请求。
- 用预期负载的倍数（例如 3 倍）来测试，而不仅仅是预期负载。

**常见错误：**只有单元测试；没有针对第 4–6 章所承诺的失败路径的测试。

---

### 11. 交付与部署

**写什么：**
- **环境**：用途、数据，以及与生产的差异。
- **CI/CD**：阶段和关卡。
- **发布与回滚**：各阶段、每个阶段之前的检查、如何关闭、如何撤销一次部署和迁移；上线就绪检查清单。

**技巧：**使用功能开关，让回滚是一个开关而不是一次部署。保持迁移向后兼容，让旧版本仍能运行。

---

### 12. 风险

**写什么：**编号、风险、可能性、影响、缓解措施、负责人。

**技巧：**每个风险都有缓解措施和负责人。包含第三方限制、数据量的意外增长，以及人员或时间方面的风险。

---

### 13. 实施计划 *（可选）*

**写什么：**里程碑，包含范围、依赖、估算、负责人。让发布日期与 PRD 的上线计划保持一致。

---

### 14. Agent 指令 *（可选）*

**作用：**当由 AI 编码 agent 根据 TRD 实现时，它需要一个有边界的上下文和明确的规则。

**写什么：**
- **上下文范围**：从哪里开始、先读什么、不要碰什么。
- **约束**：必须做什么、禁止做什么。
- **验证命令**：能证明工作完成的确切命令（lint、类型检查、测试、构建）。

**技巧：**规则要简短且可检查。命令应当原样可运行。

---

### 15. 评审检查清单，16. 附录

送审前使用检查清单。附录存放待决问题（负责人、截止日期）、术语表、参考资料和变更记录。

## 第四部分：使用 Mermaid 图表

模板使用 Mermaid，可在 GitHub、Notion、Obsidian、VS Code（需预览插件）和 [Mermaid Live Editor](https://mermaid.live) 中渲染。

**架构 / 流程**

```mermaid
flowchart LR
  C[客户端] --> A[API]
  A --> D[(数据库)]
  A --> Q[[队列]]
```

| 形状 | 语法 | 用途 |
|-------|--------|---------|
| 矩形 | `A[文字]` | 服务或组件 |
| 圆柱 | `D[(文字)]` | 数据库或存储 |
| 双括号 | `Q[[文字]]` | 队列 |
| 箭头 | `A --> B` | 调用或数据流 |
| 虚线箭头 | `A -.-> B` | 可选或异步链路 |

**实体关系**

```mermaid
erDiagram
  USER ||--o{ ORDER : places
  ORDER ||--|{ ORDER_ITEM : contains
```

基数：`||` 恰好一个，`o|` 零或一，`|{` 一个或多个，`o{` 零个或多个。名称使用下划线。

**状态图**

```mermaid

  [*] --> New
  New --> Active: approve
  Active --> Closed: finish
  Closed --> [*]
```

对于复杂的架构图，可以在图表工具里绘制，然后链接文件。

## 第五部分：质量检查清单

**追溯与范围**
- [ ] TRD 写明了所基于的 PRD 和 DRD 版本

## 第六部分：常见错误一览

| 错误 | 解决办法 |
|---------|-----|
| 重复 PRD 或 DRD | 按编号链接；只写技术后果 |
| 含糊的质量用词（"快""可扩展"） | 使用目标值、推导过程和测试方法 |
| 只有主流程 | 说明超时、重试、重复、故障、部分失败 |
| 在用户请求中调用缓慢或不可靠的服务 | 先存储，再异步处理（队列 / outbox） |
| 没有幂等性 | 增加幂等键；让消费者可安全重复执行 |
| 信任客户端校验 | 在服务端校验；客户端检查只为体验 |
| 决策没有理由 | 增加带替代方案和权衡的 ADR 行 |
| 把安全放在收尾环节 | 与设计同步建立威胁模型；测试每个缓解措施 |
| 日志里记录个人数据 | 对日志字段使用白名单；对敏感值脱敏 |
| 没人负责的告警 | 给每条告警指定负责人和运行手册 |
| 没有回滚 | 使用功能开关和向后兼容的迁移 |
| TRD 过时 | 决策变化时更新，并记录变更 |

## 第七部分：让 TRD 持续有用

TRD 的价值在于：评审人能在代码出现之前找出薄弱环节，并且半年后的值班人员能理解系统为什么这样运作。

- **尽早评审。**在决策仍然便宜可改时，就送交架构和安全评审。
- **让决策便于查找。**链接 ADR，并将被取代的标记出来而不是删除。
- **形成闭环。**上线后，将真实的量级和延迟与你的假设对比，并更新文档。
- **谨慎变更。**如果构建过程中设计发生变化，更新 TRD、记录变更，并通知依赖它的人。
